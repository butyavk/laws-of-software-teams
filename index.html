How I plan and commit

01Time boxes instead of open deadlines

Parkinson's law

Work expands so as to fill the time available for its completion

Give work a box, not a blank check

How I apply it

In my teams, the date comes first, and the scope is what we negotiate. I never set fake deadlines, because they burn teams out. Large work goes in small slices, so we can ship, re-estimate and adjust early.

02Honest estimates

Hofstadter's law

It always takes longer than you expect, even when you take into account Hofstadter's law

Plan with your history, not your hopes

How I apply it

A big task is always a risk, so I plan it step by step:

  1. If we have built something similar, I start from how long it really took, not from what we estimated.
  2. For new work, we build a quick prototype before we estimate, when we can.
  3. I compare the team's estimate with mine to calibrate both.
  4. The plan has milestones. Each one says what must be ready by its date, so a delay shows early.
  5. After the first weeks of work, a stable core team shows its real pace, and we recalculate the forecast.

To stakeholders, I give two dates: the one we aim for and the one we promise.

03Finishing: a real definition of done

The 90-90 rule

The first 90% of the code takes the first 90% of the time. The last 10% takes the other 90%

Done is not 90%

How I apply it

I plan the finish from the first day:

  1. We split big work by feature, not only by stage (code, review, test).
  2. Where it makes sense, each part is reviewed and tested on its own: the main flow first, then the main edge cases from the definition of done. Then we test the parts together.
  3. We try to follow the definition of done and not add new requests. If a real problem comes up during the work, we fix it, and this can change the timeline.
  4. Integrations with external systems can go in parallel with the core, but it depends. We need to agree on the interface early and be sure that a change to it will not mean redoing the whole integration.
  5. We measure progress by finished parts and their size, not by the number of tasks. The time left is a separate estimate, because people who finish their parts can join the remaining ones.
  6. Big work always has a buffer for the finish, and our timeline includes it. The last stage of the timeline is part of the definition of done: debugging, integration and end-to-end tests, and checks in production and, when needed, in a sandbox. The size of the buffer depends on complexity and volume. We do not use a fixed percentage.
  7. QA, product and the project lead check that a part is done.

04Scope control and saying no

Zawinski's law

Every program attempts to expand until it can read mail

Every product wants to read mail Decide on purpose if yours should

How I apply it

When a new idea comes in, I do not start with yes or no. I think it through:

  1. The product stays focused on the main problem it was built to solve. We use MoSCoW top down, for the whole product and not only for features: what it must have, and what does not fit its purpose. "It would be nice to have" is not a reason to add something.
  2. What goes into the product is a dialogue and a compromise: product mainly owns what, design how it feels, engineering how and at what cost.
  3. Pushing back is part of the job. A no comes with reasons: an alternative, the cost, the problem the request solves. The goal is agreement, and a big disagreement goes one level up.
  4. Every request gets a priority, and incidents and critical bugs are fixed at once. "Not now" is not a hidden "no": what makes sense goes to the backlog, and we return to it after the current work. Not every idea goes to the backlog. A customer request that comes back again and again gets more weight.
  5. If testing a small hypothesis from the request is more important than the current work, we take it after the current milestone. Nobody drops a task halfway, or tasks pile up and people burn out.
  6. A new feature joins the core flow or stays a separate part, depending on how closely they are linked and whether one can be used without the other.
  7. A feature that nobody uses and that has no future first goes behind a feature toggle, and later, ideally, out of the product and the code. Extra code takes developers' time. With AI agents, we can keep old code a little longer, but we still watch it.
